# Tiba Android Build Environment Audit — v191 Preservation

Date: 2026-10-16
Branch: `shadow/phase1-hardening`
Scope: read-only workflow/source review. No application code, workflow, signing configuration, or database was changed by this audit.

## Findings

1. Both Android workflows currently hard-code the operational Supabase URL:
   `https://awgppfjxegognuqozldl.supabase.co`.
   The signed workflow also embeds a publishable key in its environment. The key is a client-side publishable key, not a service-role secret, but the target project still determines which data and RPCs the app reaches.

2. The dedicated Shadow project is `bvyxiahpxogblkmtjxyx`, so the APKs generated by these workflows are not Shadow-isolated builds. Do not distribute them as test-only builds if the intent is to keep test traffic and data away from the operational project.

3. The signed workflow sets Android `versionCode=42` and `versionName=1.0.42`, while the uploaded artifact name uses the GitHub workflow run number (for this run it was labelled `v195`). Therefore the artifact label `v195` is not reliable evidence of the Android package's actual version. The build should be inspected from APK metadata before comparing it to the installed v191 APK.

4. The repository's `package.json` version is `0.0.0`; it is not the Android package version source. The workflow generates the Capacitor configuration during the build, and the generated Android Gradle files are not committed at the queried repository paths.

5. CI success proves the configured build and test commands completed. It does not prove authenticated runtime RPC compatibility, physical-device location tracking, or AI assistant behavior.

## Safe next actions

- Keep the current signed workflow and signing secrets unchanged until the release owner approves a specific release change.
- Add a separate, explicitly named Shadow build path that validates the Supabase URL against `https://bvyxiahpxogblkmtjxyx.supabase.co` and fails closed if it points elsewhere.
- Keep production/operational builds pinned to the existing operational URL; never make their target depend on an unvalidated user-controlled input.
- Verify APK metadata (`applicationId`, `versionCode`, `versionName`, signing certificate) and compare it with the installed v191 APK before treating a new artifact as an upgrade.
- Test the driver APK on a physical Android device for background/foreground location tracking, permission behavior, login, and AI assistant behavior. CI build success is not a substitute.
- Do not apply Shadow migrations until the v191 RPC/schema contract gate and clean-bootstrap sequence are reconciled and tested on the isolated target.

- No production data or project settings changed.
- No merge to `main`.
- No change to Android signing or release workflows.
- No claim that v195 is a verified replacement for v191.

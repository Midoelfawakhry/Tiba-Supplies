# Phase 1 Frontend Integration Gaps

Date: 2026-10-14

## Confirmed changes in this batch
- `LiveOperationsBoard.tsx` now creates a DRAFT order with `main_office_create_load_order` and publishes it with `main_office_publish_load_order`.
- Shadow migration `20261014270000_phase1_driver_audit_and_delivery_gate.sql` fixes driver-arrival audit ownership, adds driver-owned delivery confirmation, and requires that confirmation before Main Office can set a booking to DELIVERED.
- Read-only catalog query confirmed the relevant Main Office and driver RPCs exist with `SECURITY DEFINER` and authenticated execution grants.

## Remaining integration blockers
1. `DirectLoadAssignmentScreen.tsx` was updated to use `main_office_direct_assign(load_order_id, driver_id, vehicle_id)` and select a published order, active driver, and active vehicle. Server-side checks remain authoritative. UI build/runtime validation is still pending.
2. `DriverApp.tsx` now calls `driver_get_portal_snapshot`, `driver_get_pending_assignments`, `driver_update_live_location`, and `driver_confirm_arrival`. The portal only exposes published loads when the driver's GPS is fresh (10 minutes), accurate (<=100m on location write), and within the Ras Sedr 10km geofence. Direct assignment is active immediately in Phase 1; the legacy second-step acceptance RPC is no longer called. Driver delivery confirmation UI now calls `driver_confirm_delivery` using a fresh high-accuracy GPS reading. The RPC validates timestamp (last 10 minutes, <=1 minute future) and accuracy (<=100m). Factory destination geofencing remains unavailable because factories do not yet store destination coordinates.
3. `BranchOfficeApp.tsx` now calls `branch_get_snapshot`. The new Shadow migration adds the `BRANCH` app-user role and a read-only branch snapshot scoped to active Ras Sedr office identities. It returns published/in-progress orders, allocations, actual loading records, and active driver directory; waiting-list data is intentionally empty because Phase 1 has no queue table.
4. The driver portal now uses canonical Phase 1 states for active direct trips and history labels. The Main Office dashboard counters and order status labels were also aligned with Phase 1 states. `OfficeDirectoryScreen.tsx` now reads master directories through `main_office_get_directory`, creates factories/quarries through `main_office_upsert_directory`, and deactivates drivers through `main_office_set_directory_active`. Legacy waiting-list reads have been removed (Phase 1 has no waiting-list table). Unsupported legacy mutations for driver edits/account creation, vehicle edits, waiting-list removal, and booking redirect/cancel are explicitly guarded in the UI so they do not run against the clean schema. The directory screen remains intentionally incomplete for those operations until dedicated Phase 1 RPCs and identity workflows are designed. Added and applied `20261014310000_phase1_guard_active_directory_deactivation.sql` on Shadow so the server now rejects deactivating a driver or vehicle with an active booking; the UI also blocks driver deactivation when the dashboard snapshot shows an active trip.
5. Delivery confirmation now validates GPS timestamp and accuracy server-side. Remaining pre-production decision: add receiving-factory coordinates and a destination geofence if delivery must be confirmed only at the actual factory. The current schema does not yet model destination coordinates.
6. No authenticated test identities or operational fixtures exist; do not create fake operational data in the shared Shadow database just to make the UI appear populated. Use isolated automated tests or a disposable test project.
7. No build/lint/E2E run has been completed as part of this integration batch. GitHub reports no CI status checks for the latest UI commit. No branch-user identity or driver identity exists yet, so authenticated portal flows cannot be end-to-end exercised without provisioning controlled test identities.
